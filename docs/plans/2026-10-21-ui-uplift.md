- Date: 2026-10-21
- Spec: [../specs/2026-10-21-ui-uplift.md](../specs/2026-10-21-ui-uplift.md) (decisions D1 to D29, goals G1 to G9,
  screens and states in section 5, test-id contract and equivalences in section 7, texts in Appendix B)
- Approved reference: [`design/reference/`](../../design/reference/README.md)
- Evidence log: `docs/plans/2026-10-21-ui-uplift-evidence.md` (created by U0; every task appends a section headed
  `## U<k>` with commands and literal output only: Red, each Green, the ratchet before and after, the test counts)

## How to read this plan

- **One task, one pull request.** The pull request carries the code, the tests and the task's evidence section. Its
  body contains `Closes #<task issue>` and a `## Verify` section with Red, Green and Stub check and their literal
  results, plus the ratchet before and after. Squash-merge it yourself (`CLAUDE.md`, "Workflow").
- **The plan file on `main` wins** over the copy of a section in an issue. Read the task's section and the shared
  sections it points to ("How a preview task works", "How a screen task works", "How an e2e task works").
- **Order:** tasks run one at a time, in order. Each task issue is "blocked by" the one before it, with one
  exception. U12 and U13 need nothing from phase 2, so they wait only for U1: the loop takes them while U10 waits for
  the owner. U14 waits for U11 and U13. Owner gates (U10, U26) carry `loop:needs-human`; no loop works on them.
- **Verify blocks are the contract.** Write the tests first, run Red and keep its literal output. A task is done only
  when every Green command has been run and its output matches. "The suite is green" alone never counts.
- **Written for subagents on the sonnet model.** Decide implementation details yourself (file layout inside a folder,
  helper names, how a component is split). Never decide design: colours, sizes, spacing, copy, layout and behaviour
  come from the spec, `design/reference/` and, from U10 on, the approved preview. When the spec does not say something
  the design needs, do not invent it:
  - open an issue labelled `design-system` (template "Design system gap");
  - comment on the task issue;
  - release the task with `--needs-human`.
  This is the rule of `CLAUDE.md`, "Design system first". The one standing exception is non-colour tokens in U3
  (spec 4.2, last paragraph).
- **Never decrease** (U0 records the baseline; `scripts/ratchets.json` holds the limits from U0 on): unit, contract,
  api and e2e test counts; `uc-coverage`; the e2e `expect` count; the visual threshold `MAX_RATIO`. A limit in
  `scripts/ratchets.json` may only move in the good direction; `npm run ratchets -- --base main` checks it. The one
  exception is U25. It deletes the classic-only tests: the `ui-version` unit tests, `tests/e2e/ui-switch.spec.ts`,
  the classic e2e project, and the `expect` calls of the classic helper branches. Its evidence lists each number
  removed.
- **The classic UI does not change** until U25, except:
  - U1: the dark-token values and the re-shot dark shots;
  - U12: test ids and attributes only, nothing visible;
  - U13: today's routes move unchanged into `web/app/ClassicRoutes.tsx`, and `web/ui/toast.tsx` takes `cx` from the
    kit.
  Every classic visual test stays green with its shots.
- **Suite stays green:** every task starts with `npm ci` in its new worktree and ends with `npm run verify` exit 0
  there. Any Playwright run needs `npm run build` first because the e2e server serves `dist/web`.
- **The running console is off limits.** Never stop, restart or kill the process on `127.0.0.1:7070`, and never kill
  Node processes by name. Tests start their own servers on 7071 or on free ports (`tests/support/server-process.ts`).
  Never run `docker compose up` from a worktree, and never `docker compose down -v`.
- **English only** in every file except `shared/i18n/vi.ts`; Vietnamese texts for new keys go in `vi.ts` only. The
  owner reviews them in the `vi-*` states at U10. A quote of the owner in a repository file is written in English.
- **Issue and pull request numbers in files:** write `castraferrum#123` or a full URL, never a bare number sign
  followed by three or more digits. The coupling scan of `verify` (`scripts/lang-scan.mjs`) flags those.
- **Fonts:** the classic preview loads IBM Plex from Google Fonts (network needed the first time). The design-system
  page and the new preview load Be Vietnam Pro and JetBrains Mono from `node_modules` (`design/ds/fonts.css`, added
  by U3), so they need no network and draw the same glyphs as the app.

1. On `main`, run `npm run verify` and record in a new evidence log, section `## U0`:

2. `scripts/design-tokens.mjs <tokens.css> [--pairs <json>] [--require <json>] [--max-empty n] [--max-missing-dark n] [--max-contrast n] [--max-missing n]`.
   Every maximum defaults to 0; the script exits 1 when a count is above its maximum.
   - **Parsing.** Strip comments. A top-level rule (outside `@media`) whose selector list contains
     `[data-theme="dark"]` belongs to the dark set. Any other top-level rule whose selector list contains `:root` or
     `[data-theme="light"]` belongs to the light set. Rules of one set merge in file order. Rules inside `@media` are
     only checked for empty or swallowed declarations. A rule body splits into declarations at semicolons outside
     parentheses.
   - `empty or swallowed: N`: custom properties whose value is empty or starts with `--name:` (a declaration with no
     value swallows the next one), in any rule. List the names.
   - `missing in dark: N`: light custom properties whose value holds a colour literal (`#hex`, `rgb(`, `rgba(`,
     `hsl(`, `hsla(`) and that have no valid declaration in the dark set. List the names.
   - `--pairs` (`{ "pairs": [{ "fg": "--x", "bg": "--y", "min": 4.5 }] }`):
     - for each theme, resolve each token (the theme's own valid value, else the light value; `var(--z)` resolved
       the same way) and compute the WCAG 2 contrast;
     - print `contrast <theme> <fg> on <bg>: <ratio> < <min>` for each failure;
     - print `contrast pairs checked: P` (pairs x 2) and `contrast failures: N`.
   - `--require` (a JSON array of names): print `required tokens: R` and `missing tokens: N`. A name is missing when
     the light set lacks it, or, for a colour token, when the dark set lacks it.
   - Export the parser and the checks for the unit tests.
3. `design/contrast-pairs-classic.json`: `{ "pairs": [{ "fg": "--text", "bg": "--surface-2", "min": 4.5 }] }` (the
   hovered row of F1).
4. `scripts/design-lint.mjs [--max-title n] [--max-unknown n] [--max-literal n]`, parsing TSX with the TypeScript
   compiler API (already a dev dependency).
   - **Web rules,** over `web/**/*.tsx` except tests:
     - `native title: N`: a JSX attribute `title` on an intrinsic element (lower-case tag) or on a component named
       `Button`, `IconButton` or `ActionButton`.
     - `unknown classes: N`: class tokens from these places, checked against the class selectors of the design CSS:
       - `className="..."` and `className={'...'}`;
       - string-literal arguments of `cx(...)`;
       - the right side of `&&` and both branches of `? :` inside those arguments.
       Which CSS: if `scripts/classic-ui-files.json` exists (U13 adds it), the files it lists are checked against
       `design/components.css` plus `design/ds/components.css`, and every other file against
       `design/ds/components.css` only. Without that list, every file is checked against the design CSS files that
       exist.
     - `dynamic classes: N (not checked)`: template literals with expressions in the same places.
     - `literal styles: N`: properties of a JSX `style={{...}}` object whose value is a colour literal, a string with
       `px`, `rem` or `em`, or a number on a length property.
   - **CSS rules,** over `design/ds/components.css` when it exists. Each violation is listed with its `file:line`,
     then `css violations: N`:
     - a colour literal anywhere;
     - a `px`, `rem` or `em` length in any declaration value. Media query conditions are exempt; `0`, `auto`,
       percentages, viewport units, `fr` and unitless numbers are allowed.
     - a selector with `:hover` outside `@media (hover: hover) and (pointer: fine)`.
   - Exit 1 when `css violations` is above 0 or another count is above its maximum.
5. `scripts/ratchets.mjs [--base <git-ref>]` reads `scripts/ratchets.json` and runs every check in it. It prints each
   check's lines and then `ratchets: ok` (exit 0) or `ratchets: failed` (exit 1).
   - The JSON shape:
     ```json
     {
       "tokens": [
         { "file": "design/tokens.css", "pairs": "design/contrast-pairs-classic.json", "maxEmpty": 4, "maxMissingDark": 8, "maxContrast": 1 }
       ],
       "lint": { "maxTitle": 0, "maxUnknown": 0, "maxLiteral": 0 },
       "e2eExpectsMin": 0
     }
     ```
     A `tokens` entry may also carry `"require"` and `"maxMissing"`. The `lint` values and `e2eExpectsMin` are
     measured in step 7.
   - `e2e expects: E` counts the matches of `expect(`, `expect.soft(` and `expect.poll(` in `tests/e2e/**/*.ts` and
     `tests/support/**/*.ts`. It fails below `e2eExpectsMin`.
   - With `--base`, the same JSON at that ref (when it exists there) is the reference:
     - **Fail** when a maximum went up, when a minimum went down, or when an entry disappeared.
     - **Allowed: a new entry.**
     - **Allowed: a tombstone,** an entry replaced by `{ "file": "<same file>", "removedBy": "<task id>" }`.
     - **Allowed: a lowered `e2eExpectsMin` with a note**
       `"e2eExpectsLoweredBy": { "task": "<id>", "from": m, "classicBranchExpects": k }`, accepted only when `m`
       equals the base value and the new value equals `m - k`.
6. `scripts/phone-check.mts` (run as `node --import tsx scripts/phone-check.mts`, script `phone:check`):
   - **Server and data.** It starts its own test-mode server (`ServerProcess` from `tests/support/server-process.ts`,
     as `tests/visual/shell.visual.ts` does). Through the API it seeds one repo and two loops: one running with the
     Mock executor and a finished run, one stopped.
   - **Screens.** It opens six screens (`/`, `/loops/new`, `/loops/:id`, `/executions/:id`, `/runs/:id`, `/repos`)
     in Chromium at 390 by 844 (`isMobile`, `hasTouch`) and at 768 by 1024.
   - **UI.** With `--ui new` it opens each URL with `?ui=new`; before U13 that changes nothing.
   - **Measure.** On each screen it measures `document.documentElement.scrollWidth > innerWidth`, plus any visible
     element whose right edge passes the viewport and whose nearest scrolling ancestor is the document.
   - **Output.** It prints `<screen>@<width>: ok` or `<screen>@<width>: overflow <px>px (<selector>)`, then
     `phone overflow: k/12`. `--max k` exits 1 above k.
   - **Fixture test.** The measuring function `overflowOf(page)` is exported. `tests/visual/phone-check.visual.ts`
     (Playwright, not the CI unit job, which installs no browser) checks it on two inline fixtures: one that fits, one
     with a 600px-wide table.
7. Measure on `main` and record:
   - `npm run design:tokens -- design/tokens.css --pairs design/contrast-pairs-classic.json`;
   - `npm run design:lint`;
   - the `e2e expects` count;
   - `npm run phone:check`.
   Put the measured lint counts and E into `scripts/ratchets.json`, then wire `npm run ratchets` into `verify` and CI.

## How a preview task works (U5 to U9)

- **Where it lives.** The new preview is in `design/ds/preview/` and is built like the classic one:
  - `app.html?state=<id>&theme=light|dark` draws one state;
  - `states.js` lists the states;
  - `preview.js` holds the draw functions;
  - `data.js` is the sample world;
  - `messages.js` and `schedule.js` are generated by `npm run design:shots` and gitignored;
  - `design/ds/STATES.md` has one row per state, in the format `scripts/design-states.mjs` reads.
  `app.html` links `../tokens.css`, `../fonts.css` and `../components.css`.
- **A state's fields.** `id`, `screen`, `title`, `vp`, `fixed`, `lang`, `base` and `requires`.
  - A phone state is a separate id `phone-<id>` with `vp: [390, 844]` and `base: '<id>'`. It inherits `lang`,
    `fixed` and `requires` from its base, and its draw function is the base's.
  - Overlays (sheets, dialogs, menus, popovers, toasts) are `fixed: true`.
  - `requires` lists the test ids the matching visual test will wait for, as `id` or `id*count`. At least: the page's
    header id, its main list or card ids (with the counts the sample data fixes), and the id of any overlay or banner
    of the state.
- **Markup.** Draw functions use only the classes of `design/ds/components.css`, the markup the app will render, and
  the test ids of spec 7.1. All text goes through `t()` with the keys of spec Appendix B. New keys go into
  `shared/i18n/en.ts` and `vi.ts` in the same task. Actions are placed with the app's rule: `window.innerWidth < 640`
  means the phone.
- **Figures** are the values the server computes for the seeded sample world: how long a period has run (its start to
  its end, or to `PREVIEW_NOW`), the typical run (the loop's `avgDurationMs`), the longest active period
  (`longestExecution`), and the counts. The app will print them from the API, so the preview must print the same.
  The classic `data.js` holds pre-written figures, and some contradict its own rows: the classic visual tests mask
  those cells (`kv-avg` and `kv-longest` in `tests/visual/detail.visual.ts`). The new kit allows no such mask, so U6
  corrects them in the copy.
- **The check is the dry run** (no PNG yet; shots come at U11). `npm run design:shots -- --design design/ds --dry`
  opens every state in both themes and prints `drawn <k> states x 2 themes, 0 problems`. A problem is:
  - a JavaScript error or a missing i18n key;
  - a `requires` entry missing or with the wrong count;
  - an element class that `design/ds/components.css` does not define;
  - an inline `style` attribute with a colour literal or a `px`, `rem` or `em` length.
- **Evidence.** Each task writes screenshots of two key states into `reports/ds-preview/` (gitignored), next to the
  matching `design/reference/*.png`, and names them in the evidence log.
- **Classic untouched.** Each task checks that nothing under `design/preview/` or `design/STATES.md` changed.

## How a screen task works (U14 to U19)

1. **Read** spec sections 4, 5 and 7, `design/ds/SYSTEM.md`, the reference boards of the screen, the approved
   preview states of the screen (`design/ds/preview/app.html?state=<id>`), and the classic implementation of the same
   screen (for its data hooks and behaviour).
2. **Write the visual test first** (Red): `tests/visual/ds/<screen>.visual.ts`. It reaches every state of the
   screen's table in spec section 5:
   - in the seeded world: `tests/support/preview-world.ts` with `DS_DATA_JS`, the server and browser clocks at
     `PREVIEW_NOW`;
   - with desktop states at `PREVIEW_VIEW` and phone states at `PHONE_VIEW`;
   - reaching each state the way the classic visual test of that screen does: route holds and mocks for loading and
     error states, and `ServerProcess` where the classic test uses one.
3. **Build the screen:**
   - with kit components (`web/ui/kit/`, one file per family, text as props, no i18n, no business logic, no import
     from the classic files) and design-system classes only;
   - with data from `web/data/` (the hooks both UIs share);
   - with every test id of spec 7.1 for the screen, and the `data-status` vocabulary of 7.1;
   - with each action rendered once (`useLayout()`, spec 4.6);
   - with pages in `web/pages/<Name>Route.tsx` and new feature files in the feature folders of spec section 7.
4. **Iterate** until every compared region is at or under `MAX_RATIO`. `npm run design:compare` writes the
   side-by-side report; the new UI's is `design/compare/ds/index.html`.
5. **Masks:** only the three the kit allows (`settings-address`, `settings-version`, `stat-errors-24h`).
6. **A difference that comes from the sample data**, not from the UI (a figure of the preview that the app computes
   differently from the seeded rows), is never masked and never hidden by changing the seed or the shot. Stop:
   comment on the task issue with the state, the element, the preview value and the app value, and release the task
   with `--needs-human`. The owner decides on a corrected shot.
7. **Do not touch** the classic UI files, the classic preview or its shots.
8. **Pair count:** each task carries its own Verify block. Its pair count is the number of entries the new kit writes
   into `reports/compare/ds/results/<screen>.json` (one per state and theme).

## How an e2e task works (U20 to U23)

1. Add the task's spec files to `testMatch` of `chromium-new` in `playwright.config.ts` (as `**/<name>.spec.ts`).
2. Red: `npm run build`, then `npx playwright test --project chromium-new <files>`; record the failing test titles.
3. For every failing step:
   - a missing test id or behaviour in the new UI: fix the new UI (spec 7.1, and the preview for the look);
   - a step or an expected text that differs by design: give the helper of `tests/support/ui.ts` its new-UI branch,
     asserting the equivalent of spec 7.2 with the keys of Appendix B. Keep the helper rule: helpers return
     locators and values; the `expect` stays at the call site, and an expected text that differs is chosen there
     (`isNewUi(page) ? newText : classicText`).
   - a navigation to another origin: it goes through `gotoApp`.
4. Never delete an assertion, never loosen a classic regex, never add `test.skip` or a `@classic-only` tag. If a
   classic assertion seems to have no equivalent, stop: comment on the issue and release it with `--needs-human`.
5. Raise `e2eExpectsMin` in `scripts/ratchets.json` to the new count.
6. Each task carries its own Verify block with its files, test count and use cases.
